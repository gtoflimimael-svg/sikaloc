# Audit des actions contextuelles — Sikaloc Pro

Date de l’audit : 24 octobre 2026
Branche observée : `codex/mvp-sika-integrated`
Nature : revue statique des routes, composants, Server Actions, helpers métier et migrations référencés ci-dessous. Les parcours avec mutation n’ont pas été exercés dans le navigateur pendant cet audit.

## Principe d’autorité

La visibilité d’une action est une aide d’interface, jamais une permission. Les écritures restent contrôlées par les Server Actions, les fonctions SQL/RPC et les politiques RLS existantes. Les décisions de ce document ne modifient ni les rôles ni les règles métier.

## Corrections appliquées dans cette passe

1. Un logement avec bail actif ne reçoit plus le CTA générique de création d’annonce depuis sa ligne. Il conserve « Modifier » et une action explicite « Voir le bail » ; une annonce déjà existante reste gérable. Le parcours de disponibilité future existe séparément et ses garde-fous SQL ont été vérifiés.
2. La piste Find du dashboard différencie maintenant une disponibilité actuelle d’une préparation anticipée pendant un bail.
3. La suppression d’un locataire ou d’un bail ne s’affiche plus lorsqu’une relation connue la rend impossible, ou lorsque la lecture nécessaire a échoué. Les actions serveur et contraintes restent inchangées.
4. La liste de paiements distingue un brouillon à confirmer d’un paiement validé dont le document doit être généré. L’écran de confirmation respecte la fenêtre de correction dans ses actions visibles et traite l’erreur de lecture comme une erreur, pas comme une ressource absente.
5. Les messages serveur de suppression du logement/locataire ont été rendus exacts, sans suggérer de contourner la conservation des baux.

## Limites de l’audit

- Cet audit est fondé sur les fichiers et règles du dépôt. Les états d’annonces et de paiements ont été vérifiés dans les migrations et actions, pas au moyen de mutations Supabase.
- Les routes privées, le responsive et le mode sombre n’ont pas été validés dans un navigateur authentifié pendant cette passe.
- Les tests ajoutés couvrent des décisions de présentation pures. Ils ne remplacent pas les tests d’intégration Supabase ni une vérification réelle avec chaque rôle.
- La suppression côté serveur reste soumise à des courses de données : l’interface masque les opérations connues comme impossibles, mais les contraintes/RPC restent la protection finale si l’état change après le rendu.
